# 维护与发版（开发者向）

> 本文面向**本仓库维护者**，记录版本模型、发版流程、CI 行为与应急恢复。
> 使用者（安装 / 更新技能）请看 [docs/users/01-安装与更新.md](../users/01-安装与更新.md)。

## 一、版本模型（两层）

| 层 | 位置 | 给谁 | 怎么变 |
|----|------|------|--------|
| 单技能 `version` | 每个 `skills/<name>/SKILL.md` 的 frontmatter | 人（语义版本） | 发版时全部对齐到 tag 版本 |
| 整包 tag / Release | git tag `vX.Y.Z` + GitHub Release | 用户 / 分发 | 每次发版打一个 |
| `skillFolderHash` | 用户机 `~/.agents/.skill-lock.json` | 机器（`skills` CLI 增量检测） | 自动，不用管 |

注意：`skillFolderHash` 是 `skills` CLI 判定"有没有更新"的依据；frontmatter `version` 是人看的语义号。两者都要维护——改了技能内容 + 递增 frontmatter `version`，CLI 才能检测到更新。

## 二、发版约定

- 每次发版，**全部 20 个技能的 `version` 对齐到同一个 tag 版本**（如都改成 `1.1.0`）。
  理由：符合「打 tag 时同步所有技能 version」约定，且最不易乱。（当前 `v1.0.0` 时曾有过 `brainstorming` 为 `1.0.1` 的偏差，已对齐回 `1.0.0`。）
- 版本号语义：内容 / 文档修正 → patch；新增 / 行为变化 → minor；不兼容 → major。
- openspec CLI 版本单独锚定（见 docs/users/01-安装与更新.md），与技能版本无关。

## 三、发布流程（维护者）

1. 改完技能内容 → 把 20 个技能 `version` 全部对齐到目标版本（如 `1.1.0`）。
2. 更新 `CHANGELOG.md`：把 `Unreleased` 区内容落成 `## [1.1.0]`（补日期与对比链接）。
3. `git commit` + `git push origin main`。
4. 打 tag：`git tag -a v1.1.0 -m "..."` + `git push origin v1.1.0`。
5. CI（`release-check`）跑校验：
   - 一致性：全部技能 `version` 相同；
   - 版本匹配：`全部技能 version == tag 版本`（即 `1.1.0`）。
   - 两步通过 → 用 `GITHUB_TOKEN` **自动建 GitHub Release**（`--generate-notes`）。
6. 使用者执行 `npx skills update -g -y` 自动拉取新版。

> 本地预检（推荐发版前跑，避免云端红）：`node scripts/check-release.mjs --expected=1.1.0`

## 四、CI 行为

- 文件：`.github/workflows/release-check.yml`
- `pull_request` 到 `main`：只跑一致性校验。
- `push` `v*` tag：先跑一致性，再跑版本匹配；通过则自动建 Release。
- **红 = 版本没对齐**。红只是报警：tag 已经存在、不会自动改版本、**也不会建 Release**（Release 步骤被前面的红拦住）。它不拦截 `git push`、不影响已发布的 `main`。

## 五、应急：tag 红了怎么办

根因是版本没对齐，光删 tag 没用——先修版本再重打：

1. 修根因：把 20 个技能 `version` 对齐到目标版本 → `git commit` + `git push origin main`。
2. 删掉红 tag：`git tag -d vX.Y.Z` + `git push --delete origin vX.Y.Z`。
3. 在同份提交上重打：`git tag -a vX.Y.Z -m "..."` + `git push origin vX.Y.Z` → CI 转绿、自动建 Release。

注意：
- 删 tag **不删 Release**：若你曾手动建过 Release，需先在 Releases 页删除，否则会留孤儿。
- 已对外发布的 tag **不要删**，改发修正版 `vX.Y.(z+1)`。
- Actions 里的红 run 历史留着无妨，可作审计。

## 六、校验脚本

`scripts/check-release.mjs`（Node，跨平台）：

```bash
node scripts/check-release.mjs                    # 一致性：全部技能 version 相同
node scripts/check-release.mjs --expected=1.1.0   # 额外校验 == 1.1.0
EXPECTED_VERSION=1.1.0 node scripts/check-release.mjs   # 等价写法
```

不一致或期望值不符 → 退出码 1，并打印具体哪些技能版本对不上。

## 七、CHANGELOG 约定

- 格式：Keep a Changelog；根目录 `CHANGELOG.md`。
- `Unreleased` 区记录已提交但未随 tag 发布的改动；发版时落成 `## [X.Y.Z]` 并补日期 + 对比链接。
- 当前最新发布：`v1.0.0`（见 `CHANGELOG.md`）。
